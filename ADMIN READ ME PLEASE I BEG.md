## Before maintenance

1. Attach a physical backup device with enough capacity and mount it at
   `/mnt/minisa-recovery`. Verify it is physically independent of the NVMe
   holding `/`, `/home`, and `/srv`. Do not treat another directory or logical
   volume on that NVMe as independent storage.
2. Schedule a maintenance window. Ensure an administrator can authenticate
   with `sudo` locally. Do not disable authentication, change sudoers, or send
   passwords through chat.
3. Check both service states and current release paths:

   ```bash
   systemctl show minisa.service minisa-core.service \
     -p ActiveState -p SubState -p WorkingDirectory --no-pager
   ```

4. Have the administrator run the complete read-only preflight with an
   authenticated local sudo session. It must pass, identify the independent
   target, list required/available capacity, and include every required path.
   This command does not stop services or create a backup:

   ```bash
   sudo python3 /home/sbeppi/minisa-working-assistant-20261018/candidate/ops/capture_minisa_recovery.py \
     /mnt/minisa-recovery
   ```

   For a remote filesystem only, independently verify its storage/failure
   domain and add `--confirm-independent-target`. Never use the existing
   same-NVMe directory.

   Review and record the reported source byte estimate, available destination
   bytes, included/excluded paths, secret handling, and expected maintenance
   interruption. The script cannot estimate duration from size alone; use
   verified target throughput to set the window. Do not schedule downtime
   until the administrator has provided that estimate and a complete preflight
   result.

## Capture the full recovery point

During the maintenance window, run:

```bash
sudo python3 /home/sbeppi/minisa-working-assistant-20261018/candidate/ops/capture_minisa_recovery.py \
  /mnt/minisa-recovery --execute-maintenance
```

Enter the sudo password at the administrator's secure local prompt. The
utility stops `minisa.service` and `minisa-core.service`, acquires existing
Minisa locks without creating/truncating them, captures `/srv/minisa`, the
active code release, service unit/drop-in metadata and SQLite through the
online backup API, then restores both services to their original state. It
preserves file ownership/permissions, ACLs, extended attributes and SELinux
labels. The remote model host and systemd journal are outside this package.

Do not accept a partial output as a backup. Require the command's verified
capture result, a `CAPTURE_VERIFIED` file whose `manifest_sha256` matches the
current manifest, no `CAPTURE_INCOMPLETE` marker, all listed hashes to pass,
SQLite integrity and schema checks, and a successful disposable restore
rehearsal. A directory without the verified marker is incomplete even if it
contains a manifest. In the resulting capture directory, independently run:

```bash
cd /mnt/minisa-recovery/minisa-recovery-<capture-id>
sha256sum -c SHA256SUMS
```

The directory name is generated by the script; use the actual name. Preserve
the verified directory and do not rehearse by restoring over production.
After SIGKILL or host power loss, inspect both service states before resuming;
an in-process script cannot handle those interruptions.

Require `verified: true`, the expected ten runtime files and digest above, and


Then install the candidate and restart only `minisa.service`:

```bash

  /etc/systemd/system/minisa.service.d/20-dream-recovery.conf

```

`minisa-core.service` and the schema are unchanged. Check systemd properties,
`/health`, `/v1/dream-status`, schema version, and effective dream timeout.
Do not send test chat prompts or invoke a dream. Do not reset the recovery
circuit. Allow normal scheduling after its recovery gate and other existing
eligibility conditions.

Claim recovery only after a new durable successful dream record is verified
with its timestamp, evidence count, source/result revisions, and audit/result
metadata. Compare protected identity/CORE/personality/self-model files with
the backup. A healthy HTTP endpoint or running worker alone is not proof.

## Code-only rollback

If startup or read-only health validation fails, remove only the candidate
drop-in and start the original, unchanged release:

```bash
sudo systemctl stop minisa.service
sudo rm /etc/systemd/system/minisa.service.d/20-dream-recovery.conf
sudo systemctl daemon-reload
sudo systemctl start minisa.service
```

Do **not** restore the database for this code rollback. That preserves any
newer turns, experiences, failures, or successful dream results. Keep the
original release directory intact. A full data restore is a separate disaster
recovery decision and must not overwrite newer state without a verified
preservation copy and explicit target review.

## Do not

- Deploy without a verified independent full recovery point.
- Stop/restart services outside the planned window.
- Trigger a production dream or send qualification/test prompts.
- Clear recovery state, mark jobs successful by hand, or delete/rewrite
  experiences, jobs, journals, or evidence.
- Restore a rehearsal over production or overwrite protected identity data.
- Put the optional web-search key in notes, logs, command history, or the
  repository. Research remains a separate, undeployed candidate feature.
